# Groq API 反向代理（Netlify）实现笔记

> 目标：Groq 按 IP 地区限制、中国大陆直连 `api.groq.com` 超时时，提供一个可公开访问的转发站。
> 客户端只替换 `base_url`，其余代码不改（OpenAI SDK 兼容）。

---

## 1. 为什么这个方案成立

Groq 对来源 IP 做地区限制。Netlify Functions 运行在 AWS Lambda（默认 `us-east-2` / Ohio），
函数发起 `fetch` 时出口 IP 是美国 IP，Groq 正常响应，再把结果带回给国内访问者。

适用前提：**上游只按 IP 封锁**（不是账号 KYC / 地区注册限制）。注册、充值等网页操作仍需自行解决一次网络问题。

### Netlify Functions 的平台约束（决定设计边界）

| 项目 | 限制 |
|---|---|
| 同步函数执行 | 60 秒（不可配置） |
| 请求体 | 6 MB |
| 响应体 | 流式 20 MB / 缓冲 6 MB |
| 运行时 | Node 24，支持 Fetch API / Web Streams |
| 免费计划 | 可用（按调用次数计费） |

## 2. 架构

```
浏览器/客户端（中国大陆 IP）
   │  GET/POST /v1/*
   ▼
Netlify Edge（CDN）
   │
   ▼
Netlify Function（AWS 美国节点，us-east-2）
   │  fetch https://api.groq.com/openai/v1/*
   ▼
Groq API ──► JSON / SSE 流原路返回
```

项目只包含：

- `public/`：纯静态页面（说明 + 在线调试台），零依赖、无打包
- `netlify/functions/v1.mjs`：透明代理函数
- `netlify/functions/healthz.mjs`：健康检查（不返回任何密钥）
- `netlify.toml`：`publish` / `functions` / 安全响应头
- `tests/`：mock 上游 + 单测 + 本地预览 + CDP 验证脚本

**BYOK（Bring Your Own Key）**：访问者必须携带自己的 Groq Key。站点不存储密钥、不消耗站点所有者的额度。

## 3. 代理函数实现要点（`v1.mjs`）

### 3.1 函数格式

Netlify 现代函数（v2）是标准 Fetch API 风格：

```js
export default async function relay(req) {
  return new Response(body, { status, headers });
}
export const config = { path: ["/v1/*", "/v1"] };
```

- 入参是 Web `Request`，返回 Web `Response`
- `config.path` 是 **in-source 路由**，部署时由 Netlify 注册为真实路径（`/.netlify/functions/v1` 默认 URL 会因此禁用，属正常现象）

### 3.2 路径映射

`/v1/chat/completions` → `https://api.groq.com/openai/v1/chat/completions`。

注意 Groq 的 OpenAI 兼容前缀是 `/openai/v1`，不是 `/v1`。函数同时兼容三种前缀，便于调试：

```js
const PREFIXES = ["/v1", "/openai/v1", "/.netlify/functions/v1"];
```

### 3.3 请求头白名单

只转发必要头，避免泄露浏览器指纹与 Netlify 内部头：

```js
const REQ_ALLOW = new Set([
  "authorization", "content-type", "accept", "user-agent", "range", "openai-beta",
]);
```

同时：`x-relay-password` 不转发给上游；空 `authorization` 不发送。

### 3.4 流式透传

拿到上游响应后直接把 `body` 流交给新的 `Response`，Netlify 会逐块发送：

```js
return new Response(upstream.body, { status: upstream.status, headers: out });
```

这是整个方案体验与直连一致的关键。**不要用 `redirect` 代理**：CDN 会缓冲 SSE。

### 3.5 响应头清理（容易踩）

undici 的 `fetch` 已自动解压响应体，若原样透传 `content-encoding` / `content-length`，浏览器会二次解码失败。必须剥掉：

```js
const RES_STRIP = new Set([
  "content-encoding", "content-length", "transfer-encoding",
  "connection", "keep-alive", "set-cookie", "vary", "cache-control",
]);
```

再补 `cache-control: no-store` 与 `x-relay-version`。

### 3.6 错误映射

- 上游不可达 → `502` + OpenAI 风格 `{"error":{message,type,code}}`
- 等待响应头超时（默认 55s）→ `504`
- 上游 4xx/5xx → **原样透传状态码与 body**（SDK 依赖 401/429 的格式做错误处理）

### 3.7 CORS

- `OPTIONS` 预检直接返回 `204`，不校验密码（浏览器预检不带密码值）
- 响应头回显 `access-control-allow-origin`；`ALLOWED_ORIGINS` 可配白名单
- `access-control-expose-headers: *` 让前端读到 `x-ratelimit-*` 等头

### 3.8 可选访问密码

防止域名被扫描滥用。用常数时间比较，避免计时攻击：

```js
function sameSecret(a, b) {
  const ha = createHash("sha256").update(a).digest();
  const hb = createHash("sha256").update(b).digest();
  return timingSafeEqual(ha, hb);
}
```

### 3.9 超时控制

只对「等待响应头」计时，避免长流式被抓断：

```js
const timer = setTimeout(() => controller.abort(), 55000);
const upstream = await fetch(target, { signal: controller.signal, ... });
clearTimeout(timer); // 响应头一到就停表，body 交给 Netlify 的 60s 总限制
```

## 4. 路由与部署配置

### 4.1 最大坑：redirect 覆盖函数路由

`netlify.toml` 里**不要**为 `/v1/*`、`/health` 再写 `force = true` 的 redirect：

```toml
# 错误做法：会让函数路由全部 404
[[redirects]]
  from = "/v1/*"
  to = "/.netlify/functions/v1/:splat"
  status = 200
  force = true
```

原因：Netlify 处理请求时 **用户定义的 redirect 优先于函数的 in-source 路由**。而函数设置自定义 `path` 后，
`/.netlify/functions/v1` 默认 URL 会被禁用 —— redirect 把请求重写到一个不存在的地址，结果 404。

现象：

- 站点首页正常（静态文件）
- `/health`、`/v1/*` 全部 404
- `/.netlify/functions/healthz` 也 404（自定义路径禁用默认 URL 属正常）

修复：删掉这些 redirect，只保留函数里的 `config.path`。

### 4.2 诊断函数是否真的部署

用 Netlify API 查部署详情，`available_functions` 会列出函数与注册路由（`n` 名字、`ro` 路由）：

```bash
curl -H "Authorization: Bearer $NETLIFY_TOKEN" \
  "https://api.netlify.com/api/v1/sites/$SITE_ID/deploys/$DEPLOY_ID"
```

看到函数存在但线上 404 → 基本就是 4.1 的 redirect 问题。

### 4.3 构建配置

```toml
[build]
  publish = "public"
  functions = "netlify/functions"

[[headers]]
  for = "/*"
  [headers.values]
    X-Frame-Options = "DENY"
    X-Content-Type-Options = "nosniff"
    Referrer-Policy = "strict-origin-when-cross-origin"
```

## 5. 前端实现要点

- 纯静态 HTML/CSS/JS，无构建步骤、无外部依赖（国内加载快）
- 在线调试台：localStorage 存 Key → `/health` 展示代理状态 → `/v1/models` 动态加载模型（失败用内置兜底列表）
- SSE 解析：逐行读 `data:`，`[DONE]` 结束，最后 chunk 的 `x_groq.usage` 展示 TTFB / tokens
- 流式渲染用 `requestAnimationFrame` 节流，避免每 token 重排
- Markdown 轻量渲染：先 `escapeHtml` 再替换粗体/行内代码/代码块，防 XSS
- 移动端表格用 `overflow-x: auto` + 横滑提示

## 6. 本地测试体系（无外网也能跑）

### 6.1 mock 上游

`node:http` 起本地服务，模拟 Groq：

- `/openai/v1/models`：鉴权失败返回 401
- `/openai/v1/chat/completions`：`stream: true` 返回 SSE（含 `x_groq.usage`），否则 JSON
- `/openai/v1/audio/transcriptions`：multipart 透传
- `/openai/v1/slow`：延迟响应，测 504

### 6.2 单元测试（`node --test`，15 个用例）

路径映射、query 透传、SSE 流式、非流式 body、401 透传、multipart boundary、OPTIONS 预检、
密码鉴权（含不转发密码头）、CORS 白名单、默认函数 URL 兼容、404、502、504、healthz。

### 6.3 本地预览 & 浏览器验证

`tests/serve.mjs` 起本地服务：静态文件 + 真实调用两个函数 + mock 上游。

浏览器无头截图注意：**`--window-size=390` 会被 Chrome 最小窗口宽度限制**，造成"页面横向溢出"的假象。
用 CDP 的 `Emulation.setDeviceMetricsOverride`（390×844, mobile）才是真实移动端布局。

## 7. 线上验证清单

```bash
SITE=https://your-site.netlify.app

# 1. 函数路由与配置
curl -s $SITE/health
# => {"ok":true,"upstream":"https://api.groq.com/openai/v1",...}

# 2. 关键：不带 Key 请求 /v1/models，应返回 Groq 的 401（证明请求到达上游）
curl -s -i $SITE/v1/models
# => HTTP/1.1 401 + {"error":{"message":"Invalid API Key",...}}

# 3. 真实 Key 拉模型列表
curl -s -H "Authorization: Bearer $GROQ_API_KEY" $SITE/v1/models

# 4. 非流式对话
curl -s -H "Authorization: Bearer $GROQ_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-oss-120b","messages":[{"role":"user","content":"hi"}]}' \
  $SITE/v1/chat/completions

# 5. 流式对话（应看到 data: 行、逐字 delta、结尾 [DONE]）
curl -N -H "Authorization: Bearer $GROQ_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"openai/gpt-oss-120b","messages":[{"role":"user","content":"count 1 to 5"}],"stream":true}' \
  $SITE/v1/chat/completions
```

### 一个容易误判的测试坑

PowerShell 里 `curl.exe -d '{"json":...}'` 的双引号会被转义/吞掉，导致上游报
`invalid character 'm' looking for beginning of object key string`。
把 JSON 写成无 BOM 文件，用 `--data-binary @file` 发送即可。

## 9. 已知限制

| 项目 | 影响 |
|---|---|
| 60 秒函数上限 | 超长流式回答可能被截断 |
| 请求体 6 MB | 大音频文件需压缩/分段（Whisper） |
| 流式响应 20 MB | 普通对话足够 |
| 仅代理 Groq | 不开放任意 URL 转发，避免 SSRF |
| Netlify 国内访问 | 无大陆节点，通常可访问但延迟因运营商而异 |

## 10. 安全与运维

- **BYOK**：Key 只存在于浏览器 localStorage，随 `Authorization` 头经函数透传，不落库、不写日志
- **RELAY_PASSWORD**（可选）：防止域名被扫描白嫖 Netlify 调用额度
- **密钥管理**：任何 API Key / PAT 不要贴进聊天等非私有渠道；贴过就轮换。GitHub/Netlify PAT 权限更大，优先级高于上游 API Key
- **公开站点**：免费层有调用额度，建议设密码或关注用量

---

## 11. 可复用的判断标准

同类「上游按 IP 封锁」的问题都可以用同一模式解决：

1. 找一个有海外出口的 Serverless / Edge 平台（Netlify、Cloudflare Workers、Vercel）
2. 实现透明代理：路径映射 + 请求头白名单 + body 透传 + 响应流透传
3. 用「无 Key 请求返回上游 401」验证链路真的打通
4. 注意各平台的响应体大小与执行时长限制

Cloudflare Workers 版本只需把 `export default (req) => Response` 换成 `export default { fetch(req) }`，
其余逻辑几乎不动。
